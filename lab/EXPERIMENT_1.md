# 比赛 #1：固定 Bot 的规则迁移实验

#1 在 txcloud 的独立原生沙箱执行。按原始 ELO 选择八个不同 Bot，固定其现有版本、源码字节和 SHA-256，与 baseline、raider 测试。Bot 不作适配，不重新上传版本。#0 的配置保持不变；#1 的成绩只在比赛内统计，不进入全局 ELO、胜率矩阵或全局子榜。

## 执行批次与 500 毫秒限时

2026-11-01 根据用户要求启用 `fast500`：所有 Bot 每回合回复上限 500 毫秒，单 Bot CPU 配额 100%，继续在 txcloud 的原生沙箱执行。原 `legacy2000` 已完成的 902 场、回放和统计保留；尚未运行的旧排程停止派发。新批次完整重排同一组 28×80=2240 场，确保八个 Bot、三模式、基准和座位轮换在同一执行条件下覆盖。两个批次在实验页分别选择、分别计算排名，不混合拟合；默认显示新批次。

引擎通过 `--turn-timeout-ms` 接收限时，省略时仍为 2000 毫秒；每场结果记录实际限时和 CPU 配额。每个新结果的引擎摘要、执行配置、规则、地图、冻结座位及回放/统计均在同步导入时校验。Bot 源码、版本和物理规则保持原样。

只在旧队列排空运行中对局后切换。`experiment_transfer.py fast500` 在远端事务中保留已完成行、创建新批次并停止旧待运行行；`adopt-batch` 在生产端确认旧结果已完整回传、源摘要和完整赛程匹配后采用新批次。这些操作可重复调用，运行中的对局或不一致状态会拒绝切换。切换前后核对旧完成行摘要，备份数据库和清单。

运行服务与所有 Bot 的 scope 归入 `halite3game1.slice`，共享 CPU 190%、内存 1500 MiB 上限；单 Bot 仍独立限制 192 MiB。实际采用 2 进程、16 座位，两个工作进程分别固定在 CPU 0 和 1，子引擎和沙箱继承核心限制。未隔离核心时的 3/4 进程及双大图对照出现 Bot 超时，固定核心后的双大图与六场混合对照均无终止且成绩一致。缩短限时不会加快提前回复的回合，CPU 配额和并发的收益用实测确认。#0 与本机正在运行的补测保留原有引擎文件和执行器进程。

## 赛程与结果

每个变体 80 场，共 28 个变体、2240 场：

- 1v1：每个强 Bot 对两个基准，交换座位，共 32 场。
- 4 人：每桌两个强 Bot 加两个基准，四桌、完整四座位轮换，共 16 场。
- 8 人：每桌六个强 Bot 加两个基准，四桌分别缺席不同的一对强 Bot，完整八座位轮换，共 32 场。

全部变体使用地形种子 11。数据库种子字段另编码变体，执行时使用冻结的 `map_seed=11`。规则与人数交错排程，完成结果定时回传。相同种子的座位轮换存在相关性；单种子迁移试验不能确定普遍的规则平衡。

综合新规则为主排行，其余变体单独显示，不混合拟合。源码中可能硬编码容量、造价、返航阈值、地图尺寸或环绕距离；零造船、零搬运、协议终止需要单列。原有 Bot 的迁移成绩不能直接评价为适配新规则后策略的能力。

## 地图

基地、矿和礁石使用同一 C2 / C4 / D4 对称轨道。八人地图采用正方形格网的四次旋转加反射，不使用不能保持四方向邻接的 45° 旋转。矿由多尺度平滑噪声生成，中央富矿和矿脉使用不同权重。参考总矿目标为每玩家 60000，完整整数轨道舍入误差小于 8。

开放海域没有礁石；少礁石候选概率为 4%，常规为 12%；环岛使用带四向通道的环形礁石区。所有变体保留基地周围半径 2 的安全水域，并逐轨道检查海域和基地连通。不同地形族保持相同的矿预算。

有界规则下，越界移动作为停留，不扣移动费，可以正常采矿。视野、灵感、引擎距离、回放和诊断采用有界曼哈顿距离。Bot 自己的寻路保持原样，可能仍按环面规划。

## 船与生产

生产间隔以成功出生的回合计算，第一回合可出生。任何一艘船在碰撞中沉没都会触发损船冷却，期间禁止生产，已有船继续操作；建落点不算沉没。船数上限检查当时现存船数。生产限制拒绝出生时不扣造船费用；指令预算和合法性仍需满足引擎检查。

己方基地占用保护在卸货后、出生阶段检查。敌对三船全灭要求同格至少三船、至少两个所有者；不满足时继续按唯一最轻存活、最轻并列全灭结算。

双船型保留 `g` 指令：每玩家每第二艘成功出生的船为侦察船，其余为运输船。独立变体的侦察船容量 500、视野 6；综合规则为容量 7、视野 7。观测增加 `kind`、`capacity`、`vision_radius`，回放记录类型。既有 Bot 的命令格式保持不变。

## 整数经济与综合规则

整数经济：初始格矿 0～15、容量 15、每次采矿固定 1、初始银行 75、造船 15、落点 60、移动免费、灵感关闭。每玩家矿预算为 900。碰撞回流允许地面矿超过 15，不静默丢弃资源；回放的颜色按初始矿上限缩放，并保留真实数值。

综合规则还启用有界对称矿脉、400 步、运输船视野 5、现存船上限 24、生产间隔 2、损船冷却 2、己方占基地保护、仅敌对三船全灭，以及双船型。

## 执行与恢复

txcloud 的数据库只包含本次队列、十个冻结源文件及禁用登录的占位账号，不含生产密码、会话、Token、对话轨迹或其他 Bot。C++ 在 Bubblewrap 和 systemd 资源限制下重新编译，只有两个固定平台基准使用 Python。全局 userns 限制保持开启，通过 root 拥有的专用 bwrap 路径和 AppArmor profile 授权沙箱。

远端 `halite3-game1-runner.service` 使用一个 worker、八座位配额，支持整局失败重试、租约和已完成跳过。本机镜像队列为 `remote_queued` / `remote_running`，既有执行器只领取 `queued`，不会执行这些实验。本机网页服务可以独立更新，不需要重启正在补测的执行器。

本次部署保留本机正在补测的 `build/halite`，实验引擎另存为 `build/halite-experiment-1`，只供 #1 的地图下载预览；实际批量比赛使用 txcloud 的冻结引擎。这样既有运行中的对局及其事后记录的引擎摘要不会受到替换文件的影响。`HALITE_EXPERIMENT_ENGINE` 可以显式指定实验二进制。

`web/scripts/sync_txcloud_experiment.sh` 通过 SSH 获取一致性结果快照及公开回放。导入前核对比赛、任务、固定座位与源码哈希、引擎哈希、规则、地形种子、尺寸、回合范围和统计完整性；重复导入跳过已完成局。回传不包含源文件或 runner 私有日志。只有全部成功完成后才冻结综合规则成绩，失败局不当作完成。

远端重试和停止在远端队列操作，普通网页的重试/取消不会把任务移回本机。停止执行器使用远端 `systemctl --user stop halite3-game1-runner`；本机停止结果同步使用 `systemctl --user stop halite3-txcloud-sync.timer`。保留数据后可以从同一冻结队列继续。
